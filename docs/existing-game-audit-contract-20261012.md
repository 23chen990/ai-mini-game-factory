# 已有游戏外部审查入口：实施合同（夜市飞侠首个回归案例）

## 目标与边界
将一个独立 GitHub 游戏仓库（如 23chen990/night-market-hero）作为**只读审查目标**，不以“重新生成游戏”替代修复。所有审查必须绑定仓库 URL、不可变 Git commit、目标工作区、构建 SHA-256、证据原始字节哈希。现有 factory run 文件与游戏仓库相互隔离。实现后新增 `pnpm factory audit-existing <audit-manifest.json>`；在命令真正实现之前，不得标注可运行。

## 首期最小入口
- 输入：目标仓库、commit、runtime 入口、默认旅程、设备矩阵、不可变构建、自然输入规则及体验投诉列表。
- 输出：triage、对象×状态×渲染×视口复现矩阵、runtime product gate、独立 deterministic/natural/perceptual 三报告、七维门禁、未满足项、修复顺序和证据清单。
- 审查必须允许 `BLOCKED` / `UNKNOWN`；任何缺失的浏览器权限、原始录像、像素审查、真人盲测都不得自动替换为 PASS。
- 现有 run 通过 `workspace/game` 写权限隔离。默认目标只读；需修复时单独开游戏分支，将经复核的 issue 交给 Builder/Fixer。

## 《夜市飞侠》强制案例
1. 地图接缝：至少四处指定地图接续、前/中/后跨屏连续录像，核查建筑轮廓、颜色与边缘像素；单张静态 PNG 不足以通过。
2. 摄像机：记录 30/60/120Hz 的视口位移/速度曲线、角色投影坐标、速度峰值与失控次数；需真人舒适性记录。
3. 官兵追捕：真实触发 → 预警 → 可见逼近 → 可反制 → 正常操作实际被抓 → 失败归因 → 复起。仅坠落失败不满足。
4. 道具/载具：视野内实体出现 → 玩家能够选择触碰或错过 → 接触才发放 → 反馈与实际控制一致 → 退出后可继续；进入 segment 自动赋予不得通过。
5. 可交互场景：每个危险、挂点、平台或奖励应可触碰、可绕行、可利用恢复，或明确标记为装饰；禁止纯背景带隐形致命碰撞。
6. 竖屏遮罩、低分辨率按钮、默认新档、旧档升级、广告与钱包原子交易、恢复与离线运行分别验证。

## 修复流程
明确重现后按最早错误阶段定责（素材/蓝图/物理/摄像机/渲染/QA）。一次只修因果相关代码；每次重建后跑独立浏览器 QA。严禁让自动司机读取隐藏状态的结果冒充盲测。允许基于新证据继续修复，但需要成本/时间上限和人工中止能力；不能用删断言、放宽门槛、伪造截图或新增不相关玩法来换绿。

## 工厂自身的已确认弱点与修补
- `src/qa/experience-gates.ts` 的基础 PNG 检查只验证文件存在和非空；应以 per-feature contract v2 的对象/状态/视口/自然触发/事件顺序/独立感知审查来补充。
- `src/cli/factory.ts` 当前没有外部仓库正式审查入口。
- README 和部分文档仍描述“最多五次 FIX”，但 `.agents/skills/codex-game-repair/SKILL.md` 与 AGENTS.md 声明没有固定次数限制；必须统一到单一版本化修复政策，写单测核对文档/实现一致。
- `factory-eval/cases.json` 加入相应的假阳性回归：追捕压力永远为零、载具无接触直接发放、接缝只检查静态点、视觉危险无碰撞等。
- 不能把修复游戏失败归咎于工厂审查器，还必须提供同一构建的自然轨迹和人工验收。
