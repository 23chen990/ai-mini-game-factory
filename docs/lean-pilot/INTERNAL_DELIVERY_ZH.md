# 午间门诊 V2：目标、压力、手机操作一起改

## 修正的是生产与验收，不是再加一套 Agent

用户否定了构建 `c0322c016bfa6498070c3a6a080097c21990d087be1c4926f0b5216d3914c7f7` 的体验：不知道下一步、没紧迫感、场景不可操作。原工程绿灯不能覆盖这项反馈。旧版是已知体验失败的对照，不是已认证母版。

这次修改的对象仍是本仓库 `clinic-queue-v1` 配方，规则与存档版本升为2。没有修改原《静岚医院》业务仓库、FORM、付费模型、REA或发布状态。

## 玩家真正需要做的事

先处理初诊建档队伍，直接点场景里的挂号台派助理；下一批复诊的诊疗工作更多，需要重新看队伍决定调人。每位患者的工作量在抵达时固定，不在中途随便变慢制造压力。新批次有预告，等待与即将离开的警示反映真实时间。

点诊室才显示设备投资，点扩建区才显示房间和医生。不再用全屏常驻的五个操作按钮替代场景。横屏主布局是岗位并排；竖屏把挂号放在上方，诊疗和扩建放下方，不拉伸横屏地图。

目标从开局明示：180秒内至少接诊26人，等不及离开不超5人。不用点击次数判赢，不中途只因人数达标就显示胜利。收入改为每人6元，配合新批次调整投资节奏；不是只把原人数目标抬高。这些数值为原创实验，不是竞品恢复的参数。

## 开发与交付入口

```sh
npm run pilot -- build my-clinic-v2
npm run pilot -- prepare my-clinic-v2
npm run pilot -- delivery my-clinic-v2
```

新规则需要新工作区与新规格绑定，保留旧工作区的失败与成本，不改旧账本掩盖失败。旧浏览器存档保留在V1命名空间；V2不静默转换不兼容的班次。

`prepare` 先检查引擎与少操作基线，再做短的真实场景触摸检查，最后才跑完整默认1倍班次，减少对已知坏版本的长时间浪费。同一副本的报告、截图、实际HTML必须一致。旧绿灯、错构建或缺图不能交付。

一次完整默认速度测试本来就要3分钟，门诊检查配额改为每次最多240秒、累计15分钟，内部准备最多10分钟和2轮支持的修复。这是执行预算，不是游戏加速。合并游戏配额不变，新增付费仍为0。

## 工厂和 Skill 现在如何拦截这类问题

1. 在已有工作单增加可选 `experience`：主动调度或放置、主方向、竖屏策略、主要操作、默认速度、最小触摸范围。老工作单不会被静默改写；新门诊必须提供此要求。
2. 第一次体验不能只有一句意图：要有可观察的节点、时间窗、操作对象、结果和下一步原因。这仍是规格检查，必须继续跑实际界面。
3. 实际引擎测试三种子、四种单次操作、十个时点，合计120个对照，不只检查完全挂机。非穷尽所有策略，不宣称全局最优。
4. 实际场景触摸检查覆盖首次等队、直接点房间、局部购买、触摸取消、竖屏重排，不只是按钮44像素。
5. 默认1倍的完整HTTP班次需保留真实墙钟时间、视口、操作和结局。不用隐藏状态选操作，只在操作后读状态作断言。

动作、剧情和解谜仍使用自己的要求。放置游戏不强制制造焦虑，剧情不强制第10秒作重大选择；首次信息与阅读交互也可以是体验节点。

## 边界

这些更改不是独立模型盲审，不是真人喜欢或商业收益证明。返工器仍只修少数已知精确回归，不支持的设计问题由开发执行者处理，不再让老板写修复方案。不宣称已运行通用Codex后台工作者。

报告必须保留 `human=NOT_RUN`、`independentModelReview=NOT_RUN`、`publishable=false`。用户的体验反馈不能被测试数量覆盖。新版证明的是具体机制与操作缺口的修正，不是经验上从此不会出问题。
