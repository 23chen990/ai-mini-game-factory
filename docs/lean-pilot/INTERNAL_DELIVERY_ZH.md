# 内部发现、返工、复测后，再给老板看

## 这次要减少的麻烦

老板不应负责指出基础操作、反馈、资金和存档问题，也不应逐次回复“继续修”。开发执行者在已批准的方向与预算内完成内部检查和修复，最后只提交可玩的同一构建、简明结果和真正需要产品判断的取舍。

本轮不是另建工厂。沿用 `runner.mjs`、独立 run、研究资料和冻结的测试，增加 `prepare`（内部检查与限额返工）和 `delivery`（读回交付有效性）。保留原工程、浏览器、真人和发布判断；内部通过不是上线批准。

## 最短运行路径

```sh
# 当前分支已安装原仓库锁定依赖及 Chromium；不调用模型。
npm run pilot -- build my-clinic
npm run pilot -- prepare my-clinic
npm run pilot -- delivery my-clinic
```

`prepare` 依次运行实际引擎的三种子对照、原生回归、完整 HTTP 班次与存档流程、三尺寸的可见交互检查。已支持的具体回归由小型修复目录返回补丁，控制器检查文件范围与前置哈希后应用，再从头复测。失败版本、证据、补丁备份和耗时保留。

只有所有内部步骤在同一构建上通过，才产生 `runs/my-clinic/quality/review-<hash>.html`。`delivery` 再核对当前构建、策略、报告、截图与 HTML 字节。旧通过、重复的“passed”、缺失截图和后续改动都不能继续冒充当前可交付版本。

**`export` 仍是开发诊断工具，不代表内部审查通过。交给老板的入口应来自 `delivery`，不能拿任意旧 HTML 替代。** GitHub CI 使用相同 `prepare`，不是另一套放宽的测试。

## 实际能检查什么

- `quality-probe.mjs` 在子进程运行复制后的门诊引擎，用同样来客比较无干预、挂号支援、诊疗支援、只买设备、投资加调度。输出真实数值，不执行状态注入。
- `quality-review.mjs` 检查设备有无实际效果、投资是否付钱、空房是否被错误计作产能、旅行耗时、积压与流失、可恢复性、资金及患者守恒。UI 的自述或一份手填通过表不能取代结果。
- `quality-browser.mjs` 通过可见按钮和标签触摸操作，不借隐藏接口选“正确动作”。检查44像素操作目标、首屏范围、总成本说明、空房状态、助理支援与购买反馈、连续点击后的真实倒计时，并保存截图。它仍是脚本可见性/交互检查，不是理解画面的独立模型。
- 原 `clinic-browser-qa.mjs` 的9项检查继续保留，含全班、暂停和刷新恢复；只增加明确传入 run 根目录的能力，没有删除断言。
- `quality-review.mjs` 还演示有限剧情的有向图检查：选择不能只改按钮、终点要有回报、某分支才学到的事实不能漏进另一分支。它不审查台词自然度，不代表已生产第二个剧情母版。

## 默认返工器不是通用 AI 策划

`knownClinicRepair` 只修三种已审查、前置字节精确匹配的回归：设备失去提速、空房被错误计为诊位、触摸尺寸退化。它不能自动写新剧情或发明有趣的经营循环。

未知或设计层缺陷产生 `quality/developer-action.json`，记录观察、目标、允许文件和复测要求。**下一开发执行者应在既定范围内自行复现、修复和运行 prepare，不要把该技术清单转发给老板，让老板逐条决定怎么修。** 需要新权限、超预算或改变主方向才汇总为一次决策。

本轮没有配置或运行通用 Codex 体验审查者／修复者。可注入的程序接口只供受信测试与后续经批准的适配使用；不会从游戏、网页或JSON执行任意命令。不支持的部分明确停在开发待处理，不伪造无人值守全自动。

## 防止“为了通过而修改通过标准”

只允许修运行文件 `engine.mjs / main.mjs / index.html / style.css / themes.mjs`。测试、原始研究、输入合同和候选身份不能由返工器改动。补丁必须绑定被审查构建和原文件哈希，检查完全部补丁才写入；写入错误回滚。修复者直接改活动工作区而不返回补丁会被检测为违规。

默认最多两轮修复，内部检查累计最多300秒，外层检查预算与已有run账本同时有效。各子步骤有独立超时；这些限制不是外部模型账单控制或操作系统沙箱。仅对本仓库已审查的自有代码执行模拟，不能拿它运行不可信竞品程序。

中断的pending状态必须由开发者核查后恢复；不改run编号隐藏失败、不重置预算、不自动升级费用。`ownerMinutesSaved` 与未知缺陷召回率保持未知，不能因为少发消息就声称节省了90%人工。

## 本轮实际修正的体验问题

本轮对旧提交 `41baac6375f605380cc15e90ffd7580332118ee3` 的自有试玩作了内部查看和复现，不是让用户先报错：

1. 多个按钮小于本试点44像素目标，短屏的缺医生说明被隐藏。
2. 建房前没有明确显示房间65元、医生70元、合计135元；建完空房仍有“已生效”误导。
3. 助理×2效果和服务进度不够可见；重要的投资说明会被收入提示覆盖。
4. 每次点击都清空小于一个模拟步长的累积时间，快速重复操作会拖慢游戏。现在只有暂停、开班和状态切换重置时间基准。

对应修改增加持久的动作说明、实际服务进度条、到岗标记、完整成本、诚实的空房状态、较大触摸目标和最好班次记录；原价格、180秒班次、固定来客、引擎规则和存档格式未改变。新合同只补明确的展示与输入约束，没有把未经观察的设计假设改成事实。

同一套17项本地离线界面检查：旧版有10个失败的“检查×视口”项，新版17项通过。10不是十种独立根因。本机 HTTP 被环境限制，离线报告不代替 GitHub 的真实 HTTP；最终远端是否通过请读取本提交实际 Actions。

## 如何考核返工机制

```sh
node --test tools/lean-pilot/tests/quality-cycle.test.mjs
node tools/lean-pilot/quality-challenge.mjs ci-quality-challenge
```

第一项有真实引擎与明确标注的调度测试桩。第二项在全新隔离的 `ci-` run 里故意损坏设备效果与触摸尺寸；普通 QA 不接收故障标签，修复目录只认识已声明的回归。必须依次发现、修复、重测两轮，并回到原本被测试的代码哈希。测试不会修改主模板、测试要求或用户存档。

**故障植入验证的是这些故障的检测与返工，不是未知问题的盲测召回率，更不是“AI懂得好玩”。** 真实HTTP运行成功后才能记录闭环通过；本地测试桩不能生成有效delivery凭证。

## 后续模型只需要遵守这一条交付纪律

先查PR最新HEAD，读取本文件及当前 `quality/developer-action.json`，复现最主要的失败；在既定产品范围内修正并复测，交付绑定当前构建的HTML。不要再让老板决定按钮大小、保存细节或如何重跑命令。别新增Agent、数据库、第二个运行器、榜单或付费系统来回避当前问题。
