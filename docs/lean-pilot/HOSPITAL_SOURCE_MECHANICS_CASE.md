# 医院经营母版：代码级机制研究示范（有证据，不是已经试玩）

## 为什么写这个具体案例

以前的竞品研究通常得出“需要病人排队、雇医生、收费、扩建”等功能清单。可是《静岚医院》反复出现的体验问题，是玩家看不清忙碌、调度后果和收入代价。**要研究的不是医院里有什么，而是系统如何把需求、时间、空间、工资与风险连接为一条可体验的因果链。**

以下是对 [CorsixTH/CorsixTH](https://github.com/CorsixTH/CorsixTH) 一个公开源码快照的*源码审查*，版本固定到 commit：
06b42b221c8da5497f07504fd01039090ccdb3d5。

这是代码证据示范，不是执行过原版游戏、不代表 TH 的商业表现或证明这套精神科医院设计好玩。具体文件有各自的许可声明，复制前需单独核查；**本提案只总结机制，不把源代码、专有素材、场景和名字移植进我们的商业母版。**

## 从原代码实际得到什么

### 事实 1：队列里不只是“有没有顾客”

[原始 queue.lua 代码行 89–142](https://github.com/CorsixTH/CorsixTH/blob/06b42b221c8da5497f07504fd01039090ccdb3d5/CorsixTH/Lua/queue.lua#L89-L142) 明确区分：

- 队列总人数 size()，包括进门/出门的员工和患者；
- 实际在等待的患者 reportedSize()；
- 预计将到达的患者 expectedSize()；
- patientSize() 汇总已在排队与即将到达的患者。

[door.lua 行 69–91](https://github.com/CorsixTH/CorsixTH/blob/06b42b221c8da5497f07504fd01039090ccdb3d5/CorsixTH/Lua/objects/door.lua#L69-L91) 甚至将实际队列和预计队列分别显示在门的信息里。这意味着“病人已经在门外”和“病人正朝这个房间赶来”可以是不同的决策信号。

**对我们的因果推论（尚未验证设计效果）**：如果系统只存一个 waiting=true，玩家不可能因预知即将到来的高峰而提前分派人员。至少要区分：等待中、即将到达、接受服务、服务结束离开四种基本状态，且 UI 应能对玩家传达变化。

### 事实 2：技能有具体的时间后果

[gp.lua 行 51–91](https://github.com/CorsixTH/CorsixTH/blob/06b42b221c8da5497f07504fd01039090ccdb3d5/CorsixTH/Lua/rooms/gp.lua#L51-L91) 包含一个根据医生 skill 变化的桌面处理时间随机范围：

    inv_skill = 1 - skill
    min_time = floor(3 + 5 * inv_skill)
    max_time = ceil(8 + 10 * inv_skill)

同一分支还区分顾问医生与疲劳，并以技能参与诊断过程的概率分支。因此不能从公式推断“总诊疗时间恰好等于该抽样时间”：路线、设备使用、顾问、疲劳和后续回合还会影响过程。

**对我们的设计启示**：升级医生不能只在面板显示“效率 +20%”。它需要在同一波病人中通过服务速度、等待队列和收益变化体现。数据口径分别记录服务用时、完整就诊用时、处理量，不能混为一谈。

### 事实 3：涨价不是永远白赚

[patient.lua 行 319–339](https://github.com/CorsixTH/CorsixTH/blob/06b42b221c8da5497f07504fd01039090ccdb3d5/CorsixTH/Lua/entities/humanoids/patient.lua#L319-L339) 的 agreesToPay 函数对价格倍率大于 1 的情形使用衰减式接受概率：

    P(愿意支付) = exp(-4 * (priceMultiplier - 1))

代码对价格倍率不高于 1 的这一判断流程默认接受。该函数与 GP 分诊的后续决定共同构成“收费可能增加单客收益，也可能造成拒付离开”的压力，而不是一个孤立的收入按钮。[gp.lua 行 125–165](https://github.com/CorsixTH/CorsixTH/blob/06b42b221c8da5497f07504fd01039090ccdb3d5/CorsixTH/Lua/rooms/gp.lua#L125-L165) 还包含病人拒付离开、诊断后转诊或无可用检查房时回家的分支。

**对我们的设计启示**：资金不足应迫使玩家作取舍，例如“提价缓解现金流”与“降低价格减少流失”。但游戏实际付费比例、长期收益、对下沉市场的易懂程度，仍需要实验，不能直接照搬上述数字。

## 最重要的区别：三个规则要连起来

“增加医生”不应仅让一个数字变绿。真正可玩的经营调度反馈，应能形成：

1. 预计来客增加 → 玩家提前看见新患者路线/预计队列；
2. 实际队列变长 → 房间人满、病人等待的动效/状态明显；
3. 玩家雇医生或调整安排 → 单位时间内处理量改变，等待队列开始下降；
4. 医生成本使现金下降 → 玩家需要权衡配置，而不是无限雇人；
5. 玩家调价 → 单次收益可能改善，但患者流失风险上升；
6. 玩家看见结算差异 → 下一轮明白该先做什么。

**上面的第 1–6 步是我们自主设计的因果链候选**，不是声称已经从 CorsixTH 代码或真实录像验证了整条链。尤其“等待是否使患者离开”和“工资怎样按时扣除”尚需其它源码或运行证据，不允许把这些空白涂成已观测事实。

## 给《静岚医院》的三分钟竖切验收草案（原创设计假设）

下列时间与数值是**待调试的设计实验**，不是从竞品恢复的事实：

| 阶段 | 玩家看到什么 | 玩家该作的决定 | 候选 QA 条件 |
|---|---|---|---|
| 0–30 秒 | 第一名患者进场，明显指向缺少的服务位置 | 先开一间诊室/安排人员 | 操作后走动路线和正在处理的状态可见；没安排时不会被假自动服务 |
| 30–75 秒 | 排队和预计抵达数字上升，抱怨或情绪有可见演化 | 调班还是增开诊室 | 不干预队列持续积压；正确调度能降低实际等待时间 |
| 75–130 秒 | 正确调度带来结算改善，但工资或扩张成本造成压力 | 先买设备还是雇人 | 两种选择对短期现金和处理量产生不同结果 |
| 130–180 秒 | 新的服务需求或病患类型出现 | 用赚来的钱补第二种能力 | 新能力必须带来可见的动作/服务差异；不是单纯数值提示 |

验收不止“点击按钮后余额变化”。至少捕获三个互相关联的*玩家可见*状态：等待人数、员工工作状态、收入/损失。让测试用相同的患者输入序列比较“未安排→错安排→合理调度”三种情况。候选要保证“合理安排是更好的，但不是毫无代价”。

真实参数需通过玩法原型与真人独立试玩调整。所有公开 H5 的浏览器测试、参考报告和视频证据保留；不要把 DEBUG 注入达成目标当成玩家自然操作。

## 对母版的直接要求

首个医院压力经营母版至少必须能表示：

- 患者阶段（抵达中/等待/正在服务/完毕/退出）和各阶段计时；
- 工作人员在岗/空闲/路途/暂离与技能影响；
- 房间是否可用、服务速度与空间/排队容量；
- 来客压力、流失及收费/薪资的可见收支；
- 玩家操作对以上变量的可观察后果；
- 基于先前问题的可感知升级回报；
- 从错误到恢复的循环、可重玩的下一轮目标。

这不是一次性要求重造《主题医院》，而是**选定一个因果闭环做三分钟竖切**。母版是否可以复用，要等真实体验和实际规则对标通过后决定。具体实现应原创且遵守各来源许可证。

## 现实差距和之后使用 REA 的价值

工厂 main 的 idle-shop-v1 只有 customerWaiting 布尔属性，spatial-shop-v1 已有顾客阶段、耐心与队列：这证明问题不是“没人写模拟代码”，而是缺一套**从可信机制证据到数值、画面及玩家决策的严密联结**。

今后研究不可读源码的网页或客户端时，用 REA 找对应的函数、状态转换、计时与价格逻辑；再用实际操作、受控对照和可追踪材料判断它在屏幕上什么时候发生。这才是“母版研究先行”的交付标准。

**未完成项**：没有本次目标的实际 REA 执行、原游戏录像、运行时用户观察、真实小游戏竖切、玩家测试。此文件是有限但真实的源码级机制发现和原创设计提案，不是认证通过的母版。
