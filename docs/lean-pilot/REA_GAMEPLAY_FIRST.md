# 母版之前先做透玩法：REA 深度研究主路径（v1）

## 先纠正原先的错误前提

**不是先做一个好母版，再用 REA 修几个难点。** 用户指出以前的“竞品研究”很差，直接导致做出的经营和调度小游戏有功能、没有压力与乐趣。研究必须先给出可核验的互动规则、反馈链和成长节奏，然后才允许开发母版。

上一轮离线工具 rea-bridge.mjs / rea-cli.mjs 只支持 REA 的 **JavaScript/Electron 静态导出**以及针对单个问题的研究建议；它**不是**网页、Android、原生游戏的完整接入。84 个测试/11 个浏览器用例通过也不能证明母版好玩。请不要把它的 30 分钟单问题配额，当成一次完整母版研究的时间配额。

**新优先级：竞品深入研究 > 单循环高保真重建 > 玩家体验校正 > 可复用母版 > 后续多个产品。** 研究代码、资源与网页结构要遵守实际权利边界；借鉴常见机制不意味着可以复制专有源码、素材、关卡、角色或付费资源。

## 两类独立研究任务

1. **母版发现型（这次用户真正需要的）**：选择一款许可和获取方式明确、能真实操作的参考游戏，完整研究前 3 分钟和一段中期循环。把一个“玩家决策—系统反馈—压力后果—升级恢复”的循环查到能验证。REA 可以在取得许可的代码/程序/浏览器目标上**尽早**进入具体机制研究，不必等完整普通研究全部结束。
2. **局部排障型**：已经有游戏／合同，只剩某个模块或函数搞不懂。旧 REA bridge 的 baseline→静态导出→建议流程继续适用。其 30 分钟/2 次的建议额度只对这一类小问题有参考意义。

研究并非要求老板逐项填表，也不需要新增常驻 Agent。一个研究开发助手完成调查，另一轮独立 QA 验证，老板只需选定是否继续这个玩法母版。

## 第一步：选对标对象，不追求竞品数量

母版每次**一个主参考**、最多两个用于校正体验的辅参考。首选可实际试玩、能够合法取得信息的目标。优先：有完整许可的开放源码游戏，或可授权操作、可重复记录的 H5/网页演示；再视授权与准备工作考虑 Android APK、原生程序。**不要把先拿到一个竞品 App 名称当成完成研究。**

选择标准：与目标玩法足够接近；前 3 分钟有可观察的主要决策；存在失败压力与恢复手段；可以获得连续互动证据；其代码或二进制分析具有适当的许可、获取和访问权限。无法访问源码不意味着一定能从 REA 找到服务端规则。

## 第二步：按目标实际表面用 REA，而不是只接一种输出

| 目标材料 | 建议研究路线 | 可以带来的证据 | 不能据此宣布 |
|---|---|---|---|
| 已授权 H5 / 网页游戏 | 独立 Chrome profile + REA inspect-web-page / observe-web-session / analyze-web-bundle；需要对比时用 capture-browser-scenario、compare-web-captures；配合屏幕录像、普通输入 | 客户端加载脚本、函数线索、页面/网络生命周期、操作前后截图及行为差别 | 服务器定价、隐藏玩家留存和所有未观测运行状态 |
| 已授权 JavaScript / Electron 包 | REA analyze-javascript-application，跟踪关卡状态、计时器、事件回调与局部资源关系 | 静态模块图和有来源位置的代码证据 | 实际玩家体验、真实触控表现 |
| 已授权 Android APK / 自有模拟器 | REA inspect-android-package、search-android-classes、inspect-android-method、trace-android-references；单独做真实前台体验 | 类/方法、游戏逻辑线索与 APK 来源绑定 | 原生/Unity 全覆盖，或者未曾调用的分支已被实际触发 |

## 第三步：研究七类“玩家可以实际感受到的因果关系”

每一项都要给出“什么条件 → 玩家做了什么 → 状态如何变化 → 画面/音效怎样反馈 → 后果是什么”，并标记观察、代码派生、推断、未知。

1. **首屏至 30 秒**：第一项需要玩家决策的场景是什么？不操作会发生什么？点击或拖动后在何处看到变化？
2. **30 秒至 3 分钟**：第一个资源缺口或操作瓶颈何时出现？玩家怎样识别原因？玩家主动补救后哪里变好？
3. **循环与节奏**：生成需求、处理、收费或得分、积累、升级、出现新需求，分别由哪个事件触发？观察到几次循环？
4. **关键数值**：生产/服务用时、到达间隔、耐心、队列、收益、成本、升级价格等，能否找到公式/边界/可复测样本？公式未知就记录区间，不能乱填定值。
5. **压力与失败**：连续错误决策会造成什么可见恶化？什么是可以挽回的损失？什么是结束条件？
6. **升级和成长**：升级前后的同一场景对照；是否真的减少等待、提高产能、改变玩法，而不只是 +1 数字。
7. **下一轮与 IAA 诱因**：哪一种挫折或期待让玩家愿意继续？哪些可见奖励是**自愿**广告入口？不能由看到广告按钮推断广告 ARPDAU。

**研究深度的判据**：至少一条包含“错误决策→恶化→补救→肉眼可见改善”的可重现链，至少一个升级前后对照，至少一组可调参数，至少一个实际失败/恢复流程。不能拿到证据时标 UNKNOWN，不允许研究 Agent 为填表杜撰视频、支付数据或数值。

对经营调度类母版，不能把“有员工、顾客、价格、房间”等名词当成循环已研究。最关键的是它们**通过哪一个队列、计时、成本与满意度机制连在一起**。

## 第四步：强制产出三份而不是三十份文档

### A. 机制证据表

仅保留可影响开发的条目，字段：sourceId、固定版本/授权、原始材料路径和 SHA-256、观察到的动作/画面、代码位置/推导公式、未知与矛盾、对产品的可测影响。录像/截图本身属于观察；反编译属于派生；设计建议属于推断。哈希证明材料未被替换，不证明内容语义正确。

### B. 可开发的核心循环规格

必须包含状态机/队列流转、数值变量、升级前后同题演示、失败恢复、UI 强反馈、首 30 秒和 3 分钟的场景脚本，以及三个关键时刻的 Given/When/Then。每个高风险规则需证据索引。**只在这一步完成之后**写可复用母版代码。

### C. 参考→候选对比验收

同一行动序列分别驱动参考（实际可操作时）与自有候选；比较玩家可见行为、时间节奏、压力出现和恢复后的改进。对不能执行的参考，使用已明确范围的代码单元差异测试或多次实际观察，不把模拟样例当真人证据。候选中的 DEBUG hook 不能替代真实输入或参考行为。

**发布判定分离**：机制研究充分 ≠ 实际试玩好玩；候选可重放 ≠ 真人愿意重玩；工程 QA 通过 ≠ IAA 商业表现。

## 停止条件与预算：深度研究不能被 30 分钟误杀

一次完整母版的研究可分两段：

- **第一段：快速可行性和目标资格确认**。确认许可/运行/素材可访问、是否能观察 3 分钟流程、预计的分析引擎是否可用。若目标不可达就更换，不硬逆向。
- **第二段：集中拆一个关键循环**。合理允许数小时实际工作，先把“状态→操作→反馈→压力→恢复”挖透，避免耗一整天研究外围模块。付费调用和额外安装必须单独受控；所有失败耗时都算成本。

完整研究**没有虚假的通用 30 分钟 KPI**。建议单个初次候选的研究投入有清晰上限（例如一个工作日以内的实际工程时间，不含等待），中途能拿出可重放的三分钟循环；若持续只有模块目录和漂亮报告而无可用规则，则停止或换目标。实际开始前应记录上限，不能事后改账本。

真正的比较指标：研究加开发加 QA 加返工的总耗时、首次玩法对标通过率、第一次独立试玩能否理解和主动重玩；不是 REA 调用数量、反编译出的函数数量或测试用例数量。

## 谁来做什么

- **ChatGPT / 策划**：挑主参考、给出值得逆向的具体玩家体验问题，审阅因果链，拒绝证据不足的开发需求；避免替研究员编结果。
- **Codex / 研究执行**：在许可和工具边界内操作普通浏览器及 REA；记录真实数据、失败、局限；交机制规格，不只是研究论文。
- **Codex / 独立实现与 QA**：根据批准的规格写自有规则、复现压力场景，跑自动检查、触摸浏览器和独立人类体验；不引用未许可的代码或素材。

不需要一口气部署三个常驻 Agent，也不把母版做完才给 QA 看。先研究单循环、做 3 分钟高保真竖切、独立验收，再决定是否投入通用母版。

## 已有工厂现状：这一问题为何真实存在

- 主干 idle-shop-v1 的顾客核心是一个 customerWaiting 布尔值：它无法单独建模等待耐心、来客分布、拥堵及空间调度。
- spatial-shop-v1 比前者有实质进步：已包含顾客 phase、耐心、服务队列、进货与事件。不能笼统说工厂完全没有模拟能力；但**配置有这些字段**也不证明数值节奏、可见反馈和玩家体验已经对标。
- 现有参考录屏与参考等级 QA 能检查本方运行状态/脚本操作，但它们不会自动产出高质量、真实的竞品机制证据，更不能让假参考规格变真。
