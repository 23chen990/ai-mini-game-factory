## 为什么不直接把 #68 改指 main

1. **具体失败案例与观察**：在运行时代码提交 bde813d6 上，分支比 main 多 795 个提交，整段差异 781 个文件；其中包含其他小游戏和共享工厂变更。main 是 `5ff8d88945d76fa7dc6b3dd65aa8f9aa58324217`，共同祖先为 `f38d9955575db5561eba40007640c00094add885`。直接 retarget 会把非赛车改动一并送入审查，违反本次范围。此为已测出的范围差异，不是假设冲突。
2. **原因与替代解释**：`git merge-tree --write-tree factory-release/main HEAD` 实际退出 0，没有文本冲突。main 独有两个提交涉及 romance-story-editor 与发布注册/QA；路径检查无直接重叠。因此问题是**依赖链及合并范围**，不是已复现的文本冲突；语义兼容仍未验证，不能把 merge-tree 通过叫生产验收通过。
3. **低成本比较**：保持 #68 当前 base 最少风险且已可下载同一构建；逐个合并历史 PR 或直接 squash 整段历史会扩大审查/回归范围。后续最小安全方法是在最新 main 的隔离工作树中，按显式文件清单提取当前赛车所需依赖，而不是重建旧版。只需要一个整合者，不加 Agent/Gate。成本是一次依赖清单审查和 main 全量回归；实际 token/工时尚未测量，不虚报节省比例。
4. **保留/回退实验**：提取前记录 main 与当前候选哈希；先验证仅允许的赛车模板、构建/QA 工具、所需共享广告/油量适配及准确依赖进入 diff，其他游戏文件零变化。再在隔离 main 上重建并比较运行时文件 SHA-256、420 个源码测试、30 赛道/150 物理 AI、广告/触控浏览器套件及自然旅程。必须保留 main 独有改动。任一非赛车差异、依赖遗漏、构建不一致或回归失败即不合并，回到 #68；不能为得到绿色结果放宽标准。
