# 给下一位 Codex 的任务：母版研究先于编程（中文版）

本轮只研究并验证核心玩法机制，不要先扩充模板数量，也不要做一份浅层竞品功能列表来冒充研究。

## 输入和边界

1. 先读本分支 PILOT_START.md、REA_GAMEPLAY_FIRST.md、HOSPITAL_SOURCE_MECHANICS_CASE.md，以及主工厂已有 reference-evidence.ts/reference-level-qa.ts；确认 PR #2 HEAD 和 CI，不依赖旧摘要猜测。
2. 默认示范目标为**医院调度经营的一个三分钟核心循环**。公开代码样例为 CorsixTH，原版快照和三条已核对的源位置写在案例文件。不要把样例改写成“我们已用 REA 解开原游戏”。可读源码先直接阅读；只有在目标及版本具备实际可分析的合法包/网页/原生文件时，才使用对应 REA 接口寻找不可直接看到的客户端规则。
3. 没有安装授权/实际运行环境时，不要私自把示例 MCP 改成启用，也不要为了完成表单虚构分析结果。对于明确许可、可获取的公开网页等，也要确认操作与访问条款；用户资料、API 密钥、第三方专有源码和原始二进制不要上传公开仓库。
4. 预算：默认不支付新模型/API/工具费，不重写主工厂、不改 FORM 活跃分支、不合并 Draft。完整母版研究不能套用上一轮局部工具的 30 分钟限制；应把时间和结果分阶段记录，若目标无法分析尽早换一个可复现且有授权的目标。

## 研究产出（优先顺序）

**一、证据事实**：至少追踪三个彼此关联的真实机制，如预计队列、服务时间与收费拒绝概率。每项给出原目标固定版本、路径或录屏、可定位证据、什么被观察/推导/未知。若模拟的是原源码行为，给可复查的最小数值例；不能仅列“病人有耐心”“医生有效率”。

**二、因果循环**：以三分钟为单位写一个有错误选择、可见恶化、合理补救、付出成本、产生收益和下一目标的循环。用图/表明确事件、阶段、关键变量、UI 表现、失败恢复、玩家决策。没有证据的具体数字标设计假设并说明测试办法。

**三、测试场景**：写至少三组相同初始资源和同一来客序列下的分支对照，确保失败与成功分支在“实际等待、员工动作、现金”等玩家可见指标上形成因果差异。不要只验证按钮可点击或有字段；不要把调试接口注入误报为真实输入。

**四、早期体验评审**：基于明确来源，告诉策划 0–30 秒和 30–180 秒为什么玩家要做动作、不做会怎样；诚实指出还不知道的东西。给 5 人真人测试的最小提纲，不要在未执行时填写人类行为数据。

**五、母版开发决策**：只在 A/B/C 产物可用时提出允许开始三分钟竖切、继续调研或者换游戏的选择，并写影响的具体文件/状态。不得因为自动化单元测试数量增加就给出“可以上线”。

## REA 优先分析的问题（有合法真实目标时）

- 生成患者/顾客的计时与数量逻辑如何变化？波次、固定间隔还是状态触发？
- 等待人数、预计人数和路径/房间吞吐能力之间是否区分？显示在哪儿？
- 什么时候病人离开或拒绝付费？哪些状态/输入影响它？
- 工人技能、疲劳、岗位与设备怎样影响实际服务时长？
- 扩建和雇人是否改善了同一波顾客的处理量与利润，还是只改变数字？
- 3 分钟内是否出现玩家可识别的目标/挫折/恢复？哪些纯属产品设计？
- 对观察不到的服务器逻辑、权限不足、混淆或不支持格式，明确写 UNKNOWN/UNSUPPORTED。

每一个分析都需要绑定 REA 的原 Evidence、真实版本、退出和局限，不能单看 AI 转述。

## 交付纪律

研究质量优先，不要把所有东西封装成新 Agent、数据库、自动服务或花费多个 PR 的管理后台。把**一个可信的因果循环**做到比过去的竞品研究明显更深入，并使下一个模型能够直接写竖切代码。若还没有真实竞品运行证据，就停止在研究阶段，不凭空宣称已复刻成熟商业游戏。

改动只限独立研究目录，尽量附上可运行的最小行为对照证明。提交 PR 后贴精确 commit 和测试实际结果，说明“源码已核对／REA 未运行／参考运行时未观测／人工体验未验证”的真实状态。别制造虚假的高通过率。
